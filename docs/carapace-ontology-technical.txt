# Cortex Regenerative Process Ontology

## Technical Implementation Specification v0.1

## 0. Purpose

The Cortex Regenerative Process Ontology, or **RPO**, is the operational knowledge layer used by Carapace/Cortex to model a user’s world, processes, decisions, actions, permissions, feedback, and outcomes.

It is designed to support:

* local-first AI reasoning,
* graph-based process modeling,
* permissioned agent action,
* workflow automation,
* semantic search,
* process discovery,
* feedback-driven improvement,
* cost/yield accounting,
* and private operational intelligence.

RPO is not only a schema. It is the shared operating grammar used by:

* the local data layer,
* the knowledge graph,
* the vector index,
* the event log,
* the agent runtime,
* the workflow engine,
* the permissions layer,
* and the UI.

---

# 1. Core Architecture

RPO should be implemented as a layered local-first system.

```text
External / Local Sources
Files, folders, email, calendar, contacts, notes, browser data, forms, app APIs
        ↓
Ingestion Layer
Parsers, extractors, classifiers, metadata detectors, sensitivity detectors
        ↓
RPO Object Layer
Entities, Artifacts, Events, Agents, Processes, Flows, Regimes, Boundaries
        ↓
Graph Layer
Typed nodes, typed edges, properties, provenance, permissions
        ↓
Vector Layer
Embeddings for semantic retrieval over artifacts, chunks, summaries, objects
        ↓
Event Log
Append-only record of observations, edits, actions, feedback, approvals
        ↓
Agent Runtime
Read, reason, propose, act, update, escalate
        ↓
Workflow / Action Layer
Typed actions, validation rules, permissions, reversibility, writeback
        ↓
Materialized Views
Dashboards, process maps, task lists, client views, file views, briefs
```

The system should preserve a strong distinction between:

1. **Source data** — raw files, messages, records, app data.
2. **Ontology state** — Cortex’s current structured understanding.
3. **Derived context** — summaries, embeddings, classifications, links.
4. **Agent proposals** — uncommitted suggested changes.
5. **Committed actions** — accepted state transitions.
6. **Feedback** — user corrections, approvals, rejections, overrides.
7. **Materialized views** — UI-ready projections of the ontology.

# 2. Implementation Goals

RPO v1 should be:

## 2.1 Local-First

The default ontology state should live on the user’s device or private deployment.

Cloud should be treated as an escalation boundary, not a default assumption.

## 2.2 Event-Sourced

Every meaningful change should be recorded as an event.

The graph represents current state.
The event log explains how that state came to be.

## 2.3 Graph-Native

The ontology should model typed nodes and relationships.

Most useful intelligence comes from relationships:

* this email belongs to this client,
* this invoice belongs to this payment process,
* this task was created from this conversation,
* this action requires approval from this user,
* this repeated pattern suggests a workflow.

## 2.4 Vector-Augmented

Embeddings should support semantic search and fuzzy retrieval.

However, embeddings should not replace the ontology.

Vector search answers:

> What is similar?

The graph answers:

> What is connected?

The process layer answers:

> What is happening?

The permission layer answers:

> What is allowed?

The feedback layer answers:

> What did the user correct?

## 2.5 Permissioned by Default

Agents should never have generic access to everything.

The ontology must distinguish:

* read,
* reason,
* transform,
* propose,
* act,
* export,
* cloud-escalate,
* delete,
* and train/use-for-learning permissions.

## 2.6 Actionable

The ontology must support actions, not just descriptions.

An action should have:

* input object types,
* permission requirements,
* validation rules,
* expected yield,
* risk level,
* reversibility,
* feedback path,
* and event log output.

## 2.7 Regenerative

Every process should be capable of tracking:

* yield,
* cost,
* waste,
* burden,
* feedback,
* risk,
* and improvement over time.

# 3. Core Storage Components

## 3.1 Recommended v1 Local Stack

For a desktop/local-first product, a practical starting stack is:

```text
SQLite
Primary durable local database.

SQLite FTS5
Keyword search.

sqlite-vec / LanceDB / Qdrant local
Vector search.

Graph tables over SQLite
Typed nodes and typed edges.

Append-only event_log table
Full state transition history.

Object store / filesystem
Raw files, extracted text, thumbnails, derived artifacts.

Policy engine
Permission checks before agent reasoning/action.

Local model runtime
Ollama, llama.cpp, MLX, ONNX Runtime, or equivalent.

Optional sync layer
Encrypted cloud sync or user-controlled server.
```

Do not start with a heavy enterprise graph database unless required.

RPO can be implemented efficiently as relational tables representing graph nodes, graph edges, properties, and events.

# 7. Action Model

Actions are the kinetic layer of RPO.

Every action must pass through the following lifecycle:

```text
Created → Proposed → Validated → Approved/Rejected → Executed → Observed → Feedback Captured
```

Some low-risk actions may skip human approval if policy allows.

## 7.1 Action Execution Pipeline

```text
1. Agent proposes action
2. Validate input schema
3. Resolve target nodes
4. Check boundaries
5. Check permissions
6. Estimate cost
7. Estimate yield
8. Check reversibility
9. Require approval if needed
10. Execute handler
11. Write event log
12. Update graph state
13. Update materialized views
14. Attach feedback loop
```

# 8. Permission Model

Cortex permissions are not only about data access.

They govern cognition and action.

## 8.1 Permission Types

```text
read
Can view or retrieve the object.

reason
Can use the object as model context.

transform
Can summarize, classify, extract, embed, or derive new information.

propose
Can suggest an action.

act
Can perform a state-changing operation.

export
Can move data outside the local system.

cloud_escalate
Can send data or context to a cloud model/service.

delete
Can delete or archive.

use_for_learning
Can incorporate feedback into future behavior.

modify_schema
Can modify ontology structure.
```

## 8.2 Permission Resolution

Permission should be resolved from:

```text
User role
Agent identity
Node sensitivity
Process boundary
Regime policy
Action risk level
Locality setting
Data source policy
User override
```

## 8.3 Decision Matrix

```text
Low-risk local summary:
read + reason + transform

Draft response:
read + reason + transform + propose

Send response:
read + act + human approval

Delete file:
read + delete + human approval

Cloud escalation:
read + reason + cloud_escalate + explicit approval

Autonomous workflow:
read + reason + transform + propose + act + active feedback loop
```

## 12.1 Signals

## 12.2 Process Detection Rule

```text
IF similar events occur across time
AND involve similar agents/artifacts/actions
AND produce similar outcomes
THEN propose Pattern

IF Pattern is confirmed or confidence exceeds threshold
THEN propose Process

```

# 17. Agent Reasoning Loop

Cortex agents should follow this loop:

```text
1. Receive user intent or system event.
2. Resolve relevant process/regime context.
3. Retrieve graph neighborhood.
4. Retrieve semantic context only within allowed scope.
5. Construct RPO context packet.
6. Reason over decision/action options.
7. Estimate yield, cost, confidence, risk.
8. Check boundaries and permissions.
9. Propose action or execute if allowed.
10. Write event log.
11. Update graph state.
12. Request or capture feedback.
```

## 17.1 Pseudo-code

```ts
async function runAgentTask(task: AgentTask) {
  const scope = await resolveScope(task);

  const permission = await checkPermission({
    agentId: task.agentId,
    permission: "reason",
    targetNodeIds: scope.nodeIds,
    context: { purpose: task.purpose }
  });

  if (!permission.allowed) {
    return blockWithReason(permission.reasons);
  }

  const graphContext = await getGraphContext(scope);
  const semanticContext = await semanticSearchWithinScope(task.query, scope);
  const processContext = await resolveProcessContext(scope);

  const contextPacket = buildRpoContextPacket({
    task,
    graphContext,
    semanticContext,
    processContext,
    boundaries: permission.policyTrace
  });

  const reasoningResult = await callLocalModel(contextPacket);

  const proposedAction = await createActionProposal(reasoningResult);

  const actionPermission = await checkPermission({
    agentId: task.agentId,
    permission: proposedAction.requiresAct ? "act" : "propose",
    targetNodeIds: proposedAction.targetNodeIds,
    actionTypeId: proposedAction.actionTypeId
  });

  if (actionPermission.effect === "require_approval") {
    await writeEvent("ACTION_PROPOSED", proposedAction);
    return proposedAction;
  }

  if (!actionPermission.allowed) {
    await writeEvent("BOUNDARY_VIOLATION_BLOCKED", {
      proposedAction,
      reasons: actionPermission.reasons
    });
    return blockWithReason(actionPermission.reasons);
  }

  const result = await executeAction(proposedAction);
  await writeEvent("ACTION_EXECUTED", result);
  await updateGraphFromAction(result);
  await attachFeedbackLoop(result);

  return result;
}
```

# 19. Validation Rules

Validation rules prevent ontology drift.

## 19.1 Example Rules

```text
Every Action must have an ActionType.

Every Action must have at least one target node.

Every Process must belong to at least one Regime, unless status = proposed.

Every automated Process must have at least one FeedbackLoop.

Every high-risk Action must require human approval.

Every cloud escalation must pass a Boundary check.

Every generated Artifact must DERIVE_FROM at least one source node or user instruction.

Every Cost must identify a bearer if known.

Every Yield must identify a beneficiary if known.

Every Agent action must produce an Event.
```

# 23. Final Technical Principle

The ontology should not be a decorative philosophy layer.

It should be the runtime substrate.

Every major Cortex feature should ask:

```text
What node is this?
What process is it part of?
What regime does that process belong to?
What action is being considered?
What boundary applies?
What permission is required?
What yield is expected?
What cost is created?
What feedback will be captured?
What event records the change?
```

If the system can answer those questions, then Cortex has an actual ontology layer.

If it cannot, it is just another AI assistant with folders and embeddings.

The RPO exists to make Cortex operational, private, accountable, and regenerative.
